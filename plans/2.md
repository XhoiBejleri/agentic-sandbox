# Plan for #2: Reject CO2 values outside 0 to 500 g/km

## Goal
`POST /api/runs` will reject numeric `co2GramsPerKm` values below 0 or above 500 with HTTP 400 and the required validation detail.
Values exactly 0 and 500 remain valid; the web form will advertise the same inclusive limits, while unrelated fields, routes, and persistence remain unchanged.

## Dependencies (confirmed / plausible / open)
- confirmed, change: yes — `src/runs.ts`, `validateNewRun`: owns request validation and currently checks only number type/NaN.
- confirmed, change: no — `src/app.ts`, `POST /api/runs` and `ValidationError` handler: already maps validation failures to 400 `{ error, details }`.
- confirmed, change: yes — `test/app.test.ts`, runs API tests: add below-range, above-range, and both boundary cases.
- confirmed, change: yes — `public/index.html`, `#co2`: add inclusive HTML `min` and `max` constraints matching server validation.
- confirmed, change: yes — `e2e/smoke.spec.ts`: assert the CO2 input exposes the approved boundary attributes.
- confirmed, change: no — `src/config.ts`, `k8s/`, `README.md`: no configuration, deployment, or documented API-shape change.
- plausible, change: no — pipeline deploy/stability/smoke/browser stages should be unaffected; verify through CI after push.

## Tests
- `test/app.test.ts`: POST `-5` and `9999`; expect 400 and details containing `co2GramsPerKm must be between 0 and 500`.
- `test/app.test.ts`: POST `0` and `500`; expect 201 and the submitted boundary value in each response.
- `e2e/smoke.spec.ts`: verify `min="0"` and `max="500"` on the CO2 input.
- Run `npm run verify`.
- Run `npm run e2e` against the local app because the page changes.

## Environment contract
No environment variable is added or changed; `src/config.ts`, `k8s/configmap.yaml`, and the README environment table stay unchanged.

## Risks
- A non-number must keep the existing `co2GramsPerKm must be a number` detail without also receiving a misleading range error.
- Incorrect `<`/`>` comparisons could reject inclusive boundaries.
- Unit, build, and pipeline test stages can fail; rollout, stability, smoke, and browser stages should have no behavioral change.

## Open questions
- None.

## Decisions
- Add HTML `min="0"` and `max="500"` constraints as part of #2.
